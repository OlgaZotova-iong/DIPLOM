# Автоматизация тестирования мобильного приложения «В Хосписе»

## Обзор проекта

В рамках проекта была выполнена автоматизация UI-тестов для Android-приложения
с использованием **Espresso** и **Allure**. Работа велась по нескольким ключевым
разделам: авторизация, новости, управление новостями и цитаты. В ходе выполнения
были выявлены и решены различные проблемы, связанные с нестабильностью тестов
и особенностями работы с фреймворком.

В процессе доработки проекта по замечаниям были внесены следующие изменения:

- Тесты создания, редактирования и удаления новостей дополнены проверками
  наличия/отсутствия новости в списке (`checkNewsExistsInList` /
  `checkNewsNotExistsInList`).
- Все тестовые данные (логин, пароль, заголовки, описания, даты, время) вынесены
  в отдельный класс `TestData` для централизованного управления.
- Логика авторизации в `@Before` переработана: вместо разлогинивания и повторного
  входа перед каждым тестом выполняется проверка текущего состояния пользователя
  и логин только при необходимости.
- Во все тесты класса `NewsManagementTest` добавлено логирование шагов через
  `Allure.step()`.
- Allure-отчёт обновлён: тесты разбиты по тестовым классам с корректной структурой
  `@Epic` / `@Feature` / `@Story`.

## Авторизация

### Сравнение ручного и автоматизированного тестирования

Ручное тестирование позволяет быстро проверить основные сценарии, но требует
значительных временных затрат при повторных прогонах. Автоматизированное тестирование
даёт возможность многократно запускать тесты без участия человека, однако требует
времени на написание и поддержку кода.

- **Ручное тестирование:** 3 минуты 41 секунда
- **Автоматизированное тестирование:** 4 минуты 40 секунд

При однократном прогоне ручное тестирование показало лучшее время. Однако
автоматизированное тестирование имеет преимущество при необходимости многократного
выполнения тестов (регрессионное тестирование).

### Найденные проблемы

#### 1. Нестабильность негативных тестов авторизации (TC-003, TC-004)

Негативные тесты (`testNegativeLoginWrongCredentials_TC003` и
`testNegativeLoginEmptyFields_TC004`) оказались нестабильными при запуске через Gradle.
Причина: Toast-сообщения имеют очень короткое время отображения (около 2 секунд).
При быстром выполнении тестов через Gradle сообщение об ошибке иногда не успевает
появиться на экране до момента проверки. На Android 11+ Espresso не может
перехватить Toast-сообщения из-за изменений в системе отображения уведомлений.

Данные тесты оставлены без изменений и будут падать при запуске.
Стабильная автоматизация проверки Toast-сообщений средствами Espresso невозможна
из-за ограничений фреймворка.

### Используемые подходы

При написании тестов используется единый стиль оформления шагов через `Allure.step()`.
Все взаимодействия с элементами экрана инкапсулированы в классе `AuthPage`
в соответствии с принципами **Page Object Model**.

Метод `@Before` выполняет проверку текущего состояния: если пользователь уже
авторизован — производится выход, после чего ожидается экран авторизации.
Это гарантирует корректное начальное состояние для каждого теста без лишних
логинов и логаутов.

### Затраченное время

| Этап | Время |
|---|---|
| Настройка окружения и создание Page Object | 15 часов |
| Написание и отладка тестов | 20 часов |
| Анализ падений и доработка | 7 часов |
| Оформление отчётов | 2 часа |
| **Итого** | **около 44 часов** |

### Предварительные выводы

Автоматизация раздела «Авторизация» показала неоднозначные результаты.
Позитивные тесты выполняются стабильно. Негативные тесты с проверкой
Toast-сообщений остаются нестабильными из-за ограничений Espresso на Android 11+.
При однократном запуске ручное тестирование выполняется быстрее (3:41 против 4:40),
однако автоматизированное тестирование обеспечивает воспроизводимость результатов
при многократных прогонах.

## Новости

### Сравнение ручного и автоматизированного тестирования

При тестировании раздела «Новости» ручное тестирование выполнялось без выхода
из приложения между прогонами. Это позволило сократить время на повторные проверки.

- **Ручное тестирование:** 2 минуты 48 секунд
- **Автоматизированное тестирование:** 1 минута 26 секунд

Автоматизированное тестирование показало лучшее время благодаря оптимизации
`@Before`: логин выполняется только при необходимости, без лишних разлогиниваний
между тестами.

### Найденные проблемы

#### 1. Проблема навигации через меню (TC-013)

В процессе написания теста `testNavigateToNews_TC013` возникла проблема:
стандартные Espresso-матчеры не могли найти пункт меню «Новости». Проблема была
решена с помощью кастомного `TypeSafeMatcher`, который осуществляет поиск элемента
меню по его идентификатору (`menu_item_news`) с использованием `onData()`
и `isPlatformPopup()`.

#### 2. Проблема проверки отображения списка новостей

При проверке отображения списка новостей (`checkNewsListIsDisplayed`) стандартный
матчер `isDisplayed()` падал из-за того, что `RecyclerView` имел `height=0`
при видимом состоянии. Проблема была решена заменой на
`withEffectiveVisibility(VISIBLE)` в сочетании с ожиданием через `WaitHelper`.

### Используемые подходы

При написании тестов для раздела «Новости» используется единый стиль оформления
шагов через `Allure.step()`. Для сложных случаев навигации через меню применён
кастомный `TypeSafeMatcher`.

Для проверки стабильности добавлен тест TC-039 с многократным (5 раз подряд)
выполнением Pull-to-Refresh на главной странице. Тест TC-045 (переход в раздел
«Цитаты» из главного меню) размещён в классе `NewsTest`, так как навигация
осуществляется с главной страницы новостей.

| Этап | Время |
|---|---|
| Написание и отладка тестов | 18 часов |
| Анализ падений и доработка | 10 часов |
| Оформление отчётов | 1 час |
| **Итого** | **около 29 часов** |

### Предварительные выводы

Тесты раздела «Новости» доведены до стабильного состояния. Основные сложности
возникли при навигации через меню и при проверке отображения `RecyclerView`.
Обе проблемы были решены без использования `sleep()` и без нарушения
**Page Object Model**. После оптимизации `@Before` автоматизированное тестирование
выполняется быстрее ручного (1:26 против 2:48).

## Управление новостями

### Сравнение ручного и автоматизированного тестирования

При тестировании раздела «Управление новостями» ручное тестирование выполнялось
без выхода из приложения между прогонами.

- **Ручное тестирование:** 5 минут 2 секунды
- **Автоматизированное тестирование:** 2 минуты 27 секунд

Автоматизированное тестирование показало значительно лучшее время. Это объясняется
оптимизацией `@Before` (логин только при необходимости) и прямой навигацией
в панель управления без лишних шагов.

### Найденные проблемы

#### 1. Нестабильность тестов валидации (TC-023, TC-024, TC-025, TC-032)

Тесты, проверяющие поведение формы при отсутствии обязательных полей, изначально
опирались на проверку Toast-сообщений. Toast-сообщения имеют очень короткое время
отображения, и Espresso не имеет встроенных механизмов ожидания их появления.
Это приводило к нестабильным результатам.

Проблема была решена заменой проверки Toast-сообщений на альтернативную проверку:
метод `checkCreateNewsScreenIsDisplayed()` проверяет, что форма создания или
редактирования новости осталась на экране после попытки сохранения с невалидными данными.

#### 2. Нестабильность кнопки «Сохранить» при быстром двойном нажатии (TC-040)

При быстром повторном нажатии на кнопку «Сохранить» кнопка могла уже исчезнуть
с экрана к моменту второго клика, что приводило к падению теста. Проблема была
решена добавлением метода `tryClickSaveButton()`, который выполняет попытку
повторного нажатия в блоке `try/catch` и игнорирует исключение, если кнопка
уже недоступна.

### Используемые подходы

При написании тестов используется единый стиль оформления шагов через `Allure.step()`.
Для повышения стабильности применены следующие подходы:

- Замена Toast-проверок на проверку состояния экрана через `checkCreateNewsScreenIsDisplayed()`.
- Метод `tryClickSaveButton()` с обработкой исключения для тестирования быстрого двойного нажатия.
- Для работы с конкретным элементом списка (первая новость) применена комбинация
  `withParentIndex(0)` и `isDescendantOfA()` вместо хрупких индексных матчеров.
- Тесты создания, редактирования и удаления новостей дополнены проверками
  наличия/отсутствия новости в списке через `checkNewsExistsInList()` /
  `checkNewsNotExistsInList()`.
- Тест TC-039 (6 повторений Pull-to-Refresh) добавлен для проверки стабильности
  панели управления при интенсивном обновлении списка.

Тесты раздела «Управление новостями» приведены в стабильное рабочее состояние.
Проблема нестабильности Toast-сообщений решена путём замены на альтернативные
проверки состояния экрана. Тесты на проверку CRUD-операций дополнены проверками
списка новостей. После оптимизации `@Before` автоматизированное тестирование
выполняется значительно быстрее ручного (2:27 против 5:02).

## Цитаты

### Сравнение ручного и автоматизированного тестирования

При тестировании раздела «Цитаты» ручное тестирование выполнялось без выхода
из приложения между прогонами. Автоматизированное тестирование включало
разворачивание и сворачивание цитаты с последующей проверкой состояния.

- **Ручное тестирование:** 58 секунд
- **Автоматизированное тестирование:** 53 секунды

Автоматизированное тестирование показало лучшее время благодаря оптимизации
`@Before` и отсутствию пауз между шагами.

### Найденные проблемы

#### 1. AmbiguousViewMatcherException при проверке свёрнутого состояния цитаты (TC-047)

При написании теста на сворачивание цитаты возникла проблема
`AmbiguousViewMatcherException`. В свёрнутом состоянии на экране присутствует
несколько элементов с одинаковым идентификатором
`our_mission_item_description_text_view`, что не позволяло однозначно идентифицировать
нужный элемент.

Проблема была решена добавлением дополнительного условия `withText()` с проверкой
текста первой цитаты. Это позволило однозначно идентифицировать элемент и проверить,
что он не отображается на экране после сворачивания.

### Используемые подходы

При написании тестов для раздела «Цитаты» используется единый стиль оформления
шагов через `Allure.step()`. Для взаимодействия с элементами `RecyclerView`
применялся `RecyclerViewActions.actionOnItemAtPosition()`, что позволило обращаться
к конкретному элементу списка по индексу без использования хрупких матчеров.

Проверка свёрнутого состояния реализована через комбинацию `withId()` и `withText()`
с условием `not(isDisplayed())`. Решение не требует использования `sleep()`
и не нарушает принципы **Page Object Model**.

| Анализ падений и доработка | 6 часов |

### Предварительные выводы

Тесты раздела «Цитаты» успешно автоматизированы и проходят стабильно. Основная
сложность заключалась в работе с несколькими элементами, имеющими одинаковый
идентификатор. Проблема была решена путём уточнения матчера через `withText()`

## Приведение проекта к единому стилю и доработка по замечаниям

### Выполненные изменения

В рамках финальной доработки проекта по замечаниям были выполнены следующие изменения:

**Проверки CRUD-операций:**
Тесты создания, редактирования и удаления новостей дополнены проверками наличия
или отсутствия новости в списке после выполнения операции. Используются методы
`checkNewsExistsInList()` и `checkNewsNotExistsInList()` в `ControlPanelPage`.

**Централизованное хранение тестовых данных:**
Все тестовые данные (логин, пароль, заголовки новостей, описания, даты, время)
вынесены в отдельный класс `TestData`. Это обеспечивает возможность централизованного
изменения данных без правки каждого теста по отдельности.

**Оптимизация @Before:**
Во всех тестовых классах (кроме `AuthTest`) метод `@Before` переработан:
вместо разлогинивания и повторного входа перед каждым тестом выполняется проверка
текущего состояния пользователя и логин только при необходимости. Это значительно
сократило время выполнения тестов.

**Логирование шагов:**
Во все тесты класса `NewsManagementTest` добавлено логирование шагов через
`Allure.step()`. Теперь все тестовые классы используют единый стиль оформления шагов.

**Структура Allure-отчёта:**
Тесты разбиты по отдельным тестовым классам с корректной иерархией
`@Epic` / `@Feature` / `@Story`. Allure-отчёт обновлён и актуализирован.

## Выявленные проблемы и способы их решения

### 1. Нестабильность негативных тестов авторизации (TC-003, TC-004)

Негативные тесты авторизации остаются нестабильными из-за ограничений Espresso
при работе с Toast-сообщениями на Android 11+. Тесты оставлены без изменений.
Стабильная автоматизация проверки Toast-сообщений средствами Espresso невозможна
из-за ограничений фреймворка.

### 2. Нестабильность тестов модуля управления новостями

В модуле управления новостями были выявлены и устранены проблемы нестабильности.
Toast-проверки заменены на альтернативные проверки состояния экрана через
`checkCreateNewsScreenIsDisplayed()`. Для теста быстрого двойного нажатия на кнопку
«Сохранить» добавлен метод `tryClickSaveButton()` с обработкой исключения.

### 3. AmbiguousViewMatcherException при работе с RecyclerView

В разделе «Цитаты» при работе с несколькими элементами, имеющими одинаковый
идентификатор, возникала проблема `AmbiguousViewMatcherException`. Проблема была
решена путём уточнения условий поиска элементов через комбинацию `withId()`
и `withText()`.

## Технические ограничения

При подключении библиотеки `allure-android` возникли конфликты зависимостей
(dependency conflict) с текущей конфигурацией проекта. В качестве альтернативы
используется `allure-kotlin`, которая поддерживает аннотации
(`@Epic`, `@Feature`, `@Story`, `@Description`) и логирование шагов (`Allure.step()`),
но не поддерживает автоматическое прикрепление скриншотов при падении тестов.
По этой причине скриншоты в Allure-отчёте отсутствуют.
