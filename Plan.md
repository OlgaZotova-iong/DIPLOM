# План проверки и автоматизации мобильного приложения «В хосписе»

## 1. Объект и цель тестирования

**Объект:** мобильное приложение «В хосписе» (FMH Android), версия 15.03.24, платформа Android.  
**Цель:** подтвердить соответствие функционала требованиям, выделить сценарии для автоматизации и обосновать, какие кейсы целесообразно оставить ручными.

## 2. Подход к тестированию

Тестирование проводится комбинированным способом:

- **Автоматизированные проверки** — для стабильных, атомарных сценариев с предсказуемыми UI‑элементами (авторизация, базовые CRUD‑операции, переходы).
- **Ручные проверки** — для сценариев со сложной UI‑логикой (кастомные календари, RecyclerView, Pull‑to‑Refresh), внешних переходов и субъективной оценки (форматы, вёрстка).

## 3. Приоритезация тест‑кейсов

Приоритет определяет очерёдность и обязательность проверки:

- **High:** критические сценарии, без которых приложение не может считаться рабочим (авторизация, создание/удаление новостей, базовые переходы).
- **Medium:** важные сценарии, влияющие на удобство и соответствие ТЗ (сортировка, фильтрация, редактирование, граничные значения).
- **Low:** вспомогательные сценарии (версия, копирайт, внешние ссылки).

## 4. Словарь статусов в Check.csv

- **Passed:** поведение соответствует ожидаемому.
- **Failed:** обнаружено расхождение с требованиями.
- **Blocked:** тест не мог быть выполнен по внешней причине (например, сервер недоступен).

## 5. Критерии завершения

Тестирование считается завершённым, если:

1. Все тест‑кейсы из Cases.csv прогнаны и имеют статус в Check.csv (Passed/Failed/Blocked) с пояснением.
2. Для кейсов с «Автоматизация: Да» автотесты написаны и стабильно запускаются.
3. Для кейсов с «Автоматизация: Нет» в колонке «Причина отказа от автоматизации» указано обоснование.

## 6. Инструменты и формат файлов

- **Ручное тестирование:** устройство Samsung Galaxy A16 (Android 14).
- **Автоматизация:** Espresso (Java) + Android Studio.
- **Отчётность:** Allure (для автотестов).
- **Файлы:** Cases.csv и Check.csv с разделителем `;`, кодировка UTF‑8.

## 7. Распределение по автоматизации и причины отказа

Автоматизация применяется к сценариям с простыми и стабильными UI‑элементами. Отказ от автоматизации обоснован техническими ограничениями:

- нестабильные локаторы (кастомные View, динамические ID, анимации);
- сложная логика UI (кастомный календарь, RecyclerView с кастомными элементами);
- внешние переходы (открытие ссылок в браузере);
- действия, которые сложно эмулировать (нажатие «вне элемента»);
- субъективная проверка (форматы дат, обрезка текста, вёрстка).

## 9. Риски и меры реагирования

| Риск | Вероятность | Влияние | Меры реагирования |
|------|-------------|---------|-------------------|
| Сервер приложения недоступен | Высокая | Критическое | Использовать статус `Blocked` в Check.csv, фиксировать даты простоя, планировать прогон на периоды стабильной работы. По возможности использовать моки/заглушки для ключевых API. |
| Медленная работа эмулятора в Android Studio | Высокая | Среднее | Параллельно вести ручное тестирование на реальном устройстве (Samsung Galaxy A16). Для автотестов закладывать дополнительное время на прогон и стабилизацию ожиданий. |
| Частые изменения требований/UI | Средняя | Среднее | Вести журнал изменений требований, приоритизировать автоматизацию только стабильных сценариев. Кейсы с «плавающими» элементами помечать как «Автоматизация: Нет». |
| Нестабильные локаторы в кастомных элементах | Высокая | Высокое | При написании автотестов использовать устойчивые атрибуты (content‑desc, текст, иерархия), избегать хрупких XPath/ID. Проводить ревью локаторов после каждого релиза. |

## 11. Что не тестируется

- Регистрация (отсутствует в приложении).
- Серверная часть (тестируется только клиент).
- Производительность и нагрузочное тестирование.
- Глубокие проверки безопасности (XSS, инъекции) — только базовая проверка отображения спецсимволов.

## 12. Формат файлов и соответствие колонок

### Cases.csv

Колонки:  
`ID;Приоритет;Раздел;Заголовок;Предусловие;Шаги;Ожидаемый результат;Автоматизация (Да/Нет);Причина отказа от автоматизации`

Связь с Check.csv — по полю `ID` (TC‑...).

### Check.csv

Колонки (актуализированные):  
`ID;Название;Статус;Примечание;Дата выполнения`

**Особенности соответствия:**

- Поле `Название` в Check.csv заполняется как краткое описание кейса (обычно — значение из колонки `Заголовок` Cases.csv, при необходимости сокращённое до 1–2 строк).
- Поле `Примечание` содержит детализацию результата (фактическое поведение, выявленные дефекты, нюансы).
- Поле `Дата выполнения` указывается в формате `ГГГГ‑ММ‑ДД` для единообразия и корректной сортировки в Google Таблицах / Excel.
